## Design report (verbatim)

**B4 DESIGN REPORT: money ledger. No code written.**

Base: main 7f54ec5, B2 and B3 designs assumed. Entries re-read: 010, 011, 013, 015, 016, 017, 073, 075, 080. Charge model confirmed from source: separate charges and transfers (platform PaymentIntents, later `stripe.transfers.create` with `source_transaction` and `transfer_group = bookingId`); no direct charges anywhere. Every register mechanism holds. Nine further defects were found in the survey and are folded in as named additions (B4.9) for your ruling.

Invariants B4 relies on from B3: I1 one accepted owner per slot; I2 COMPLETED written once by CAS inside the window, so `releaseDueAt` is set exactly once; I3 cancellation and completion mutually exclusive, so a refund on cancel and a release on complete never start from the same state; I4 override-status is plain, so a booking completed by override has no `releaseDueAt` and surfaces in the queue as `COMPLETED_NO_RELEASE_CLOCK`.

**B4.1 Schema and the derived refund state (RENA-010, RENA-011, RENA-080).**

New models (Prisma, exact):

```
model TransferSlice { id, bookingId, stripeTransferId String @unique, amountPence Int?, reversedPence Int @default(0),
  kind TransferSliceKind (ANCHORED | EXCESS | ADOPTED), sourceChargeId String?, status TransferSliceStatus (CREATED | PARTIALLY_REVERSED | REVERSED | NEEDS_RECONCILE),
  idempotencyKey String? @unique, attempt Int @default(0), createdAt, updatedAt; @@index([bookingId]) }
model TransferReversal { id, transferSliceId, refundRecordId, stripeReversalId String? @unique, amountPence Int,
  status (PENDING | SUCCEEDED | UNKNOWN | FAILED), idempotencyKey @unique, attempt, lastReconcileResult String?, createdAt, updatedAt }
model RefundSlice { id, refundRecordId, stripePaymentIntentId, stripeChargeId String?, requestedPence Int, executedPence Int @default(0),
  stripeRefundId String? @unique, status (PENDING | SUCCEEDED | FAILED | UNKNOWN), idempotencyKey @unique, attempt, lastReconciledAt, lastReconcileResult String?, createdAt, updatedAt;
  @@index([refundRecordId]) }
```

Columns added: `RefundRecord.requestedPence Int`, `RefundRecord.executedPence Int @default(0)`; `TopupRecord.stripeChargeId String? @unique`; `Booking.amountShortfallPence Int?`; `ServiceAddon.cleanerSharePct Decimal(5,4)?`; `Dispute.resolvingSince DateTime?`, `Dispute.resolutionAmountPence Int?`, `Dispute.lastMoneyError String?`. Enum `DisputeStatus` gains `RESOLVING_REFUND`, `RESOLVING_RELEASE` (its own migration file, ordered first, since an added enum value cannot be used in the transaction that adds it). `Booking.stripeTransferId` stays populated for one batch as a compatibility mirror of the first slice and is dropped in B9. `RefundRecord.allocation` stays for one batch, read only by the backfill, dropped in B9.

Derivation, pure functions in `src/lib/money/ledger.ts`, tested exhaustively:

- `refundRecordStatus(slices)`: UNKNOWN if any slice UNKNOWN; PENDING if any PENDING and none UNKNOWN; SUCCEEDED iff Σ executed = requested; PARTIAL iff 0 < Σ executed < requested and all slices final; FAILED iff Σ executed = 0 and all final. `REVERSAL_ONLY` is no longer written; existing rows map to FAILED with their reversal rows present.
- `bookingRefundState(chargedPence, slices)`: `executed = Σ executedPence over SUCCEEDED slices of every record of the booking`; `paymentStatus = REFUNDED iff executed >= chargedPence; PARTIALLY_REFUNDED iff 0 < executed < chargedPence; else unchanged`, with `chargedPence = round(totalAmountCharged × 100)` (never `totalPrice`). `recomputeBookingRefundState(tx, bookingId)` writes it inside the same transaction as any slice confirmation. Nothing else writes `paymentStatus` REFUNDED or PARTIALLY_REFUNDED.
- `cleanerSharePence(booking, refundPence) = round(cleanerEarningsPence × refundPence / chargedPence)`, the one formula for reversal and for earnings scaling (replaces the `totalPrice` ratio at `refund.service.ts:776`).

**B4.2 Transfers and reversals (RENA-010, addition N1).**

`transfer.service.ts releaseBookingFunds`: unchanged claim (`transferStatus in [PENDING, UNKNOWN, FAILED, RELEASING] → RELEASING`) and reconciliation by `transfer_group`; every transfer found or created becomes a `TransferSlice` row (ADOPTED for pre existing ids; ANCHORED with `sourceChargeId`; EXCESS with none). Anchored headroom per charge is that charge's own amount: the original charge gets at most `originalChargePence − anchoredAlready(original)`, and each succeeded top up charge (now stored on `TopupRecord.stripeChargeId`) gets its own ANCHORED slice up to its amount; the remainder is one EXCESS slice. Idempotency keys unchanged in shape, `release_${bookingId}_v${attempt}` and `…_x`, plus `release_${bookingId}_t${topupRecordId}_v${attempt}` for top up anchored slices. RELEASED iff Σ slice amountPence >= transferPence. `setFailed` and `setUnknown` become guarded (`WHERE transferStatus = 'RELEASING'`).

Reversal (`refund.service.ts executeReversal`): target = `cleanerSharePence`; allocated across slices proportionally to `(amountPence − reversedPence)`, largest remainder, never exceeding a slice's remaining; per slice `stripe.transfers.createReversal(sliceTransferId, { amount, metadata: { refundRecordId, transferReversalId } })` with key `reversal_${refundRecordId}_${sliceId}_v${attempt}`; `TransferReversal` row PENDING before the call, SUCCEEDED after, UNKNOWN on a connection or API error after one same key retry; the slice's `reversedPence` and status update with it. A slice with `amountPence` null (NEEDS_RECONCILE after backfill) refuses the refund with `LEDGER_RECONCILIATION_PENDING` until the scheduler fills it.

**B4.3 Refunds as slices (RENA-011, additions N2, N3, N4, N5).**

`refundBooking` keeps its guards, now against the derived aggregate: `refundable = chargedPence − executed`. Allocation (LIFO over succeeded top ups, then the original) writes one `RefundSlice` per PaymentIntent, PENDING, with key `refund_${refundRecordId}_${sliceId}_v${attempt}`, before any Stripe call. Each slice is executed independently: SUCCEEDED with `executedPence = refund.amount`, FAILED on a definitive error, UNKNOWN after one same key retry on a connection or API error (retry always with the slice's own PaymentIntent, fixing N2). After every slice outcome: `recomputeBookingRefundState` and the record's derived status in one transaction. Earnings scaling before release uses `cleanerSharePence` (N3). Remainder helpers: `remainingRefundablePence(booking)` used by cascade exhaustion (N4), stuck jobs and dispute (N5); `retry-refund/route.ts` is deleted, replaced by the queue's actions. Unknown slice reconciliation: `stripe.refunds.list({ payment_intent })`, match `metadata.refundSliceId`, write the truth (SUCCEEDED with the amount, or FAILED when absent after 24h and the PaymentIntent shows no refund), `lastReconcileResult` recorded.

`charge.refunded` webhook: look the charge up by `Booking.stripeChargeId` or `TopupRecord.stripeChargeId`; for each `charge.refunds.data[i]`: a slice with that `stripeRefundId` or with `metadata.refundSliceId` → confirm it; no match → create a RefundRecord `triggeredBy 'STRIPE_DASHBOARD'` with one SUCCEEDED slice; then `recomputeBookingRefundState`. The webhook never reads `charge.amount_refunded >= charge.amount` for the booking state. Idempotency: the slice confirmation is a guarded `updateMany` (`status in [PENDING, UNKNOWN]`), so a duplicate event changes nothing; the receipt row creation handles P2002 as "already received" instead of 500.

**B4.4 Disputes (RENA-013, addition N6).**

`AdminOperationsService.resolveDispute`: one interactive transaction: `dispute.updateMany({ where: { id, status: { in: ['OPEN','UNDER_REVIEW'] } }, data: { status: outcome === 'release-to-cleaner' ? 'RESOLVING_RELEASE' : 'RESOLVING_REFUND', resolution, resolvingSince: now, resolutionAmountPence } })` and `booking.updateMany({ where: { id, status: 'DISPUTED' }, data: nextBookingStatus… })`; if either count is 0 the transaction throws and the route answers 409; nothing is written. Then the money step: refund (RESOLVING_REFUND) via `refundBooking`, and for split, on refund SUCCEEDED, `dispute.updateMany RESOLVING_REFUND → RESOLVING_RELEASE` then `releaseBookingFunds`; release (RESOLVING_RELEASE) via `resumePausedRelease`. RESOLVED is written only by `dispute.updateMany({ where: { id, status: { in: ['RESOLVING_REFUND','RESOLVING_RELEASE'] } }, data: { status: 'RESOLVED', resolvedAt } })` after the money step confirms (refund record SUCCEEDED, or transfer RELEASED); the final resolution messaging is sent there. On a definitive failure the dispute stays RESOLVING with `lastMoneyError`; a new scheduler job `retryResolvingDisputes` (every tick, rows with `resolvingSince < now − 2min`, 20 per tick) re runs the money step idempotently (same record and keys); the queue shows the row with Retry. State table:

| dispute              | booking  | event                            | next                                                              |
| -------------------- | -------- | -------------------------------- | ----------------------------------------------------------------- |
| OPEN or UNDER_REVIEW | DISPUTED | resolve refund or split          | RESOLVING_REFUND, booking CANCELLED (refund) or COMPLETED (split) |
| OPEN or UNDER_REVIEW | DISPUTED | resolve release                  | RESOLVING_RELEASE, booking COMPLETED                              |
| RESOLVING_REFUND     | any      | refund SUCCEEDED, outcome refund | RESOLVED                                                          |
| RESOLVING_REFUND     | any      | refund SUCCEEDED, outcome split  | RESOLVING_RELEASE                                                 |
| RESOLVING_RELEASE    | any      | transfer RELEASED                | RESOLVED                                                          |
| RESOLVING\_\*        | any      | failure                          | unchanged, lastMoneyError, retried                                |

**B4.5 Shortfall (RENA-017).** `processPaymentSuccess`: when `pi.amountReceived < expectedPence`, the paid transition still happens, and in the same `updateMany` `amountShortfallPence = expected − received` and `transferStatus = 'PAUSED'`; audit `PAYMENT_SHORTFALL`. ## Rulings and amendments (James, 2026-10-07)

B4: as designed, with:

- DB uniqueness on Stripe transfer, refund and reversal identifiers.
- Legacy data is never guessed: adopted legacy transfers migrate NEEDS_RECONCILE with null amounts until Stripe is queried; legacy RefundRecord SUCCEEDED is not proof of executed money, any slice not provable from a stored Stripe identifier migrates UNKNOWN/NEEDS_RECONCILE and blocks affected money actions until reconciled.
- Retry and backoff metadata on resolving disputes and unknown operations (short retries, then backoff, persistent failures visible in stuck-money, UNKNOWN reconciled not re-executed).
- N7: unreleased funds get a chargeback hold, a chargeback after release becomes CHARGEBACK_AFTER_RELEASE in stuck-money, and release resumes only when `moneyHoldReasons(booking)` is empty (dispute, shortfall, chargeback coexist).
- N9: deterministic stored idempotency key, one same-key retry, then UNKNOWN reconciled by the sweep, never a new-key replacement charge while UNKNOWN.
- N8: admin-managed PlatformConfig defaults are create-if-missing, never reset on deploy.
- Add-on payout follows the parent service's rate unless the add-on defines its own (products stays 90%); the misleading fee controls removed; the four service-page copy changes sanctioned.
- Rollback documentation states that old-code rollback after the first new-format money mutation is not automatically safe.
- Migration rehearsed twice on production-shaped data; full diff review (money); gate review on Fable 5.1 if available.
