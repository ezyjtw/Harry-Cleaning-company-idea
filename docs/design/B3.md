**B3.1 One assignment helper (RENA-012, RENA-030, half of RENA-028). Overlap E.**

Files and functions:

- New `src/lib/booking/assign.ts`: `assignCleaner(input)`, the only function allowed to write `cleanerId` on a row in the blocking status set or to move a row into that set.
- New `src/lib/time/booking-time.ts`: `bookingStartUtc`, `bookingEndUtc`, `londonOffsetMs` (moved out of `quiet-hours.ts` and exported), used by the helper's overlap arithmetic and by B3.2's windows.
- `src/lib/availability/slot-eligibility.ts`: `filterSlotAvailableCleaners` gains a `db` parameter (the transaction client) and uses `bookingStartUtc`; semantics otherwise unchanged.
- Callers rewired, each with its exact CAS predicate (table below).

Exact contract:

```
assignCleaner({
  bookingId, cleanerId,
  expect: { status, cascadePhase?, cleanerId?, provisionalCleanerId? },  // every given key must equal the row
  requireUnexpiredOffer: boolean,            // cascadeExpiresAt IS NULL OR cascadeExpiresAt > now
  slot?: { date, startTime, durationHours }, // default: the row's own; rescueRebook passes the new slot
  data: BookingUpdateInput,                  // the target write; must set status and cleanerId (or provisional fields)
  actor: { kind: 'CLEANER'|'ADMIN'|'SYSTEM', id? }
}) => { ok: true, booking } | { ok: false, reason: 'NOT_FOUND'|'STATE_CHANGED'|'OFFER_EXPIRED'|'SLOT_TAKEN' }
```

Steps, inside one `prisma.$transaction(async tx => …)`, default READ COMMITTED:

1. `SELECT pg_advisory_xact_lock(hashtextextended('cleaner:' || $1, 0))` with `cleanerId`. Every writer for that cleaner serialises here; the lock releases at commit or rollback.
2. `tx.booking.findUnique({ where: { id } })`. Missing → NOT_FOUND.
3. Compare every key in `expect` with the row → STATE_CHANGED on any mismatch. If `requireUnexpiredOffer` and `cascadeExpiresAt !== null && cascadeExpiresAt <= now` → OFFER_EXPIRED.
4. Overlap re-read inside the transaction: `filterSlotAvailableCleaners([cleanerId], { …slot, excludeBookingId: id }, tx)`; empty → SLOT_TAKEN. Because every writer for the cleaner holds the lock, any competing assignment is either committed (and visible to this read) or has not started.
5. `tx.booking.updateMany({ where: { id, ...expect, ...(requireUnexpiredOffer ? { OR: [{ cascadeExpiresAt: null }, { cascadeExpiresAt: { gt: now } }] } : {}) }, data })`; `count === 0` → STATE_CHANGED (a non-cleaner actor, for example a customer cancel, changed the row between steps 2 and 5).
6. Return the re-read row. Side effects (notifications, audit, emails) run by the caller only on `ok: true`.

Invariant I1, stated exactly: for any cleaner C and any instant, the set of bookings with `cleanerId = C` whose status is in `blocksCleanerSlotWhere()` (CONFIRMED, ACCEPTED, EN_ROUTE, IN_PROGRESS, COMPLETED, REVIEWED, DISPUTED, SCHEDULED, or AWAITING_CLEANER with PRIMARY_OFFER) has pairwise non-overlapping intervals, where an interval is `[bookingStartUtc − buffer, bookingEndUtc + buffer]` and buffer is the cleaner's `bookingBufferMinutes`. Rows with startTime `Flexible` keep today's semantics (they do not block and are not blocked; parked below).

Payment success with SLOT_TAKEN (the chosen cleaner lost the slot between booking and paying): the customer has paid, so the transition still happens. The helper is called with `data` as above; on SLOT_TAKEN the caller writes the same transition with the primary added to `declinedCleanerIds` and then calls `advanceFromPrimary(bookingId)`, whose own CAS (PRIMARY_OFFER → BACKUP_OFFER) moves the offer to backups. No customer is ever refused after paying. Customer chosen creation (`POST /api/bookings`) keeps its existing slot check, now also run under the lock through the helper's read path, and still creates PENDING (not blocking); the blocking moment is payment success, above.

Not through the helper, by design and said so: admin override-status (`override-status/route.ts`) stays a plain audited `update`, your ruling. Named risk: it performs no slot check; the queue in B4 will show a booking completed by override with no release clock, and nothing else changes. `AdminOperationsService.assignCleaner` has zero callers: deleted (deviation: the entry routes it through the helper; dead code is deleted instead).

Exclusion constraint: not added in B3. Reason: the blocked interval depends on a per cleaner buffer, on a status set, and on a London wall clock conversion, and `startTime` may be `Flexible`; a correct `EXCLUDE USING gist (cleanerId WITH =, interval WITH &&) WHERE status IN (…)` needs a generated `tstzrange` column that cannot represent those rows. Recommended as later hardening once Flexible is retired or represented; the advisory lock plus the in-transaction re-read is the invariant's guarantee now.

Migration or config: none. Automated tests: B3.5. Delivery WEB. Proof RIG-AUTO.

**B3.2 Lifecycle compare and swap and the D-f windows (RENA-028, RENA-027, RENA-032). Overlap E.**

Files and functions:

- `src/lib/time/booking-time.ts`: `bookingStartUtc(date, startTime): Date | null` (date is the stored UTC midnight; startTime "HH:MM" is London wall clock; `Flexible` or unparsable → null), `bookingEndUtc(date, startTime, durationHours)`, and `transitionWindow(target, booking, now): { allowed: boolean, opensAt: Date | null }` with constants `EN_ROUTE_LEAD_MS = 2h`, `IN_PROGRESS_LEAD_MS = 30min`, `COMPLETE_BEFORE_END_MS = 30min`. Rules: EN_ROUTE allowed iff `now >= start − 2h`; IN_PROGRESS iff `now >= start − 30min`; COMPLETED iff `now >= end − 30min`; CANCELLED has no window. Conversion: wall = `Date.UTC(y, m, d, HH, MM)` from the date's UTC fields; `instant = wall − londonOffsetMs(wall)`, then one correction pass `instant = wall − londonOffsetMs(instant)` (handles the two transition days).
- New `src/lib/booking/transition.ts`: `transitionBooking({ bookingId, cleanerId, from, to, now, actor })` → `{ ok: true, booking } | { ok: false, code: 'INVALID_TRANSITION'|'TOO_EARLY'|'STATE_CHANGED', opensAt? }`. Steps: validate `VALID_TRANSITIONS[from]` includes `to`; `transitionWindow` (skipped for `actor.kind === 'ADMIN'`, the override route); `updateMany({ where: { id, cleanerId, status: from }, data })` where data per target is exactly today's (`arrivalConfirmed`, `checkedInAt`, `completedAt` plus `releaseDueAt` 24h or 6h, or `cancelledAt` plus reason plus cascade nulls); `count === 0` → STATE_CHANGED.
- `src/app/api/cleaner/jobs/[id]/route.ts` PATCH: `from` is the status it read; responses: INVALID_TRANSITION 400 (unchanged), TOO_EARLY 422 `{ error: 'TOO_EARLY', target, opensAt }`, STATE_CHANGED 409 `{ error: 'STATE_CHANGED', hint: 'refetch' }`. Side effects (`completedJobs` increment, audit, customer notifications) run only on `ok: true`, so a double tap writes once and notifies once. The legacy `status: 'ACCEPTED'` branch delegates to `acceptWithReconciliation`, the same function the accept route uses (deviation: today it calls `atomicAccept` directly and skips reconciliation).
- Decline: `cascade.service.ts handleDecline` and `decline/route.ts`: the two plain updates (the `declineReasons` read modify write, and the `declinedCleanerIds` push) become one statement: `UPDATE "Booking" SET "declinedCleanerIds" = array_append("declinedCleanerIds", $cleaner), "declineReasons" = coalesce("declineReasons", '{}'::jsonb) || $entry::jsonb WHERE id = $id AND status = 'AWAITING_CLEANER' AND "cascadePhase" = $phaseRead AND NOT ($cleaner = ANY("declinedCleanerIds"))` via `$executeRaw`; 0 rows → `{ advanced: false, reason: 'STATE_CHANGED' }` and no cascade advancement from the stale read. Advancement then uses the existing guarded helpers.
- Paid cleaner cancel keeps `initiateCleanerCancelRescue` (already CAS). Unpaid cancel goes through `transitionBooking`.
- UI: the Today page, Jobs, job cards and the web job page render the 422 body: "You can set On my way from {opensAt London clock}" and the same shape for Start and Complete; a 409 triggers the existing refetch (`__renaRefresh`). Pro shell: no OTA; the page renders the server's refusal.

Exact state table for the cleaner PATCH (from → to, guard, window):

| from                                                     | to                      | CAS WHERE                     | window      |
| -------------------------------------------------------- | ----------------------- | ----------------------------- | ----------- |
| ACCEPTED                                                 | EN_ROUTE                | status ACCEPTED, cleanerId    | start − 2h  |
| EN_ROUTE                                                 | IN_PROGRESS             | status EN_ROUTE, cleanerId    | start − 30m |
| EN_ROUTE                                                 | COMPLETED               | status EN_ROUTE, cleanerId    | end − 30m   |
| IN_PROGRESS                                              | COMPLETED               | status IN_PROGRESS, cleanerId | end − 30m   |
| PENDING, AWAITING_CLEANER, CONFIRMED, ACCEPTED, EN_ROUTE | CANCELLED (unpaid only) | status = from, cleanerId      | none        |

Invariant I2: COMPLETED is reached from EN_ROUTE or IN_PROGRESS only, by CAS, inside the window; `releaseDueAt` and `completedAt` are written in that same statement, so they are written at most once per booking. Invariant I3: because customer cancel (`cancellation.service.ts` guarded `updateMany`), admin cancel, and the cleaner's transitions are all CAS on `status`, cancellation and completion are mutually exclusive; the loser's side effects never run.

Flexible startTime (parked, recommendation given): windows cannot be computed. Proposal: EN_ROUTE and IN_PROGRESS allowed from 06:00 London on the booking day; COMPLETED from 06:00 plus duration minus 30 minutes. Your ruling.

Migration or config: none. Delivery WEB. Proof RIG-AUTO.

**B3.5 Regression matrix (RENA-033), exact cases.**

Integration, vitest against rig Postgres, file `src/lib/booking/assign.integration.test.ts`, opt in `BOOKING_LIFECYCLE_INTEGRATION=1` plus `DATABASE_URL` (the scheduler lease pattern), added to the CI integration step. Fixtures: synthetic users `cleaner-a@integration.invalid`, `cleaner-b@…`, `customer-a@…`, created and deleted per test; no real people.

1. Two overlapping offers, one cleaner, accepted simultaneously (`Promise.all` on two `atomicAccept` calls, 30 repetitions): exactly one row ACCEPTED, the other AWAITING_CLEANER with `SLOT_TAKEN` returned; never two ACCEPTED.
2. Two cleaners accepting the same COMBINED_OFFER booking simultaneously: exactly one wins; the loser gets STATE_CHANGED.
3. Non overlapping offers (slot B starts after slot A end plus buffer): both ACCEPTED.
4. Expiry: `cascadeExpiresAt = now − 1s` → OFFER_EXPIRED, row unchanged; `now + 1s` → ACCEPTED; `null` → ACCEPTED.
5. Sweep racing accept: `processExpiredCascadeWindows` and `atomicAccept` concurrently on a row expiring now: final state is exactly one of (ACCEPTED by the cleaner) or (phase advanced and accept refused), never both, 30 repetitions.
6. Chosen cleaner: `processPaymentSuccess` (PENDING → PRIMARY_OFFER for cleaner A) racing `atomicAccept` of another overlapping booking by A: final state has at most one blocking row for A in that slot; the paid booking is never left PENDING; when it lost the slot it sits in BACKUP_OFFER with A in `declinedCleanerIds`.
7. Cancellation racing completion: customer cancel and cleaner COMPLETED concurrently from IN_PROGRESS, 50 repetitions: final status ∈ {COMPLETED, CANCELLED}; exactly one of `completedAt`, `cancelledAt` is set; `completedJobs` incremented iff COMPLETED; never a refund record and a `releaseDueAt` together.
8. Double tap complete: two concurrent PATCH COMPLETED: one 200, one 409; one audit row; `completedJobs` plus one.
9. Decline racing sweep: concurrent `handleDecline` and phase sweep: `declinedCleanerIds` gains the cleaner at most once; the phase advances exactly once.
10. Provisional finalise against a slot taken meanwhile: `writeTopupSuccess` returns SLOT_TAKEN and the booking stays PROVISIONAL_APPROVAL with the top up recorded SUCCEEDED and flagged for the B4 queue (money taken, assignment failed; B4's queue state `TOPUP_WITHOUT_ASSIGNMENT`).

Unit (pure): the window boundary table for each target at `opensAt − 60s` (refused) and `opensAt` (allowed), on 2026-03-29 and 2026-10-25 (BST transitions) and for a 23:30 start with 2h duration (COMPLETED allowed from 01:00 next day London).

Playwright on the rig (Stripe not reachable; release itself is proven in B4 with the SDK mocked): verified cleaner happy path to COMPLETED with `releaseDueAt` set; backup acceptance with the loser's 409; stale offer shows "This offer has expired"; premature On my way shows the opensAt message; deletion blocked by a live job and by a pending payout; Stripe onboarding return states (existing room, stubbed API). Cleaner session invalidated in the shell: covered by B1's watcher tests, referenced not repeated.

## Rulings and amendments (James, 2026-10-07)

B3: as designed, with:

- Flexible-time jobs may enter EN_ROUTE and IN_PROGRESS from 06:00 London, must enter IN_PROGRESS before COMPLETED, and COMPLETED is anchored to checkedInAt + duration − 30 min; fixed-time windows as ruled (−2h, −30m, end −30m), admin override outside the invariant and audited.
- The full twelve-helper Europe/London sweep rides B3 with explicit tests for nonexistent spring times (rejected as invalid booking times) and ambiguous autumn times (the later occurrence, documented), midnight crossing and 23:30 plus multi-hour durations; no bespoke London→UTC conversion remains.
- Pre-accept serializer: outward postcode plus town, first name, service, date/time, duration, property characteristics, structured extras, supplies, cleaner earnings; no paymentStatus; context is a documented structured object or excluded.
- Deletion blockers: provisional assignment blocks; backup, reserve and unaccepted offer membership do not (the cascade skips the cleaner instead).
- Dead assignCleaner deleted; exclusion constraint deferred and documented; PATCH acceptance through reconciliation; renaFindAccept gains the payment guard.
- Gate review on Fable 5.1 if available, else the full concurrency results table is the review.
